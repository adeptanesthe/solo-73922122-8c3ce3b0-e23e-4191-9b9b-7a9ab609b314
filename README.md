# 横拍转竖屏 9:16 裁切工作台

横拍的手工课素材改竖屏：在**原图内按原高**裁出 9:16 竖窗，保证手与工件（逐帧必留框）
始终完整留在画面里，并让裁切轨迹在时间上尽量平滑、画面信息量尽量大。

## 功能

- 上传至多 **80 张**有序、同尺寸 PNG 帧 + 逐帧必留框 JSON（转正后帧边长 ≤ 512，高为 16 的倍数）。
- **EXIF 方向感知**：读取每帧 PNG `eXIf` 方向标记（1–8，含镜像与 90° 旋转），必留框按“文件存储方向”校验原框后逐帧换算，图片/框/锁定/预览统一在转正坐标系对齐；`/api/frame/{i}.png` 仍原样返回上传字节。
- 每帧裁切窗高 = 转正后图高 H，宽 = 9H/16，仅横坐标 x 可变；每帧窗口**覆盖全部必留框**。
- 轨迹约束：相邻帧横移 `|Δx| ≤ 8`；连续两次有向横移之差 `|Δxᵢ₊₁ − Δxᵢ| ≤ 2`。
- 目标：最大化各帧窗口内**横竖相邻像素灰度差绝对值之和**（二阶动态规划全局最优）。
- 逐帧查看裁切结果（原图 + 裁切窗 + 9:16 竖屏预览），可**拖动**裁切窗并**锁定/解锁**任一帧；
  改动某一帧锁定位置后重新求解，前后未锁定帧自动跟着调整。
- 若接不出完整轨迹，报告**从首帧起最早接不上的一帧**，显示该帧原图并撤下竖屏预览。
- 上传被拒（解码失败、尺寸/框不合法等）时保留当前旧素材、锁定与预览。
- 内置三段样片：A（可解）、B（第 12 帧工件瞬移，演示不可解）、C（A 的混合 EXIF 朝向版本，覆盖方向 1–8，转正后与 A 完全一致，轨迹与总能量也完全相同）。

## 启动

```bash

# 打开 http://localhost:8000
```


## 必留框 JSON 格式

```json
{
  "frames": [
    [[x0, y0, x1, y1], ...],
    ...
  ]
}
```

- 顶层也接受裸数组（等价于 `frames` 的值）。
- 长度必须等于帧数；每帧可为空数组（该帧无必留框）。
- 框为像素区间 `[x0, x1) × [y0, y1)`，使用**该 PNG 文件存储方向**下的像素坐标（即不手动应用 EXIF 方向时的像素网格），须在存储画面内；服务端先按存储尺寸校验原框，再按该帧 EXIF Orientation 换算到转正坐标系。
- 因此给带方向标记的帧填框时，直接在“未转正的原始像素”上量坐标即可；若先把图片和框一起转正再上传，在相同锁定下会得到完全一致的裁切轨迹、总能量与无解失败帧。
- 转正后裁切窗高为整帧高，故只有 x 方向影响可行性。
- 上传多帧时按文件名自然序排列（frame_2 在 frame_10 前）。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/upload` | multipart：`frames`（多个 PNG）+ `boxes`（JSON 文件） |
| POST | `/api/load_sample?name=a\|b\|c` | 载入内置样片（也支持 `sample_<名称>` 下的其他安全命名素材） |
| POST | `/api/solve` |  body `{"locks": {"帧号": x}}` → 轨迹或 `fail_frame` |
| GET  | `/api/frame/{i}.png` | 第 i 帧**上传时的原始 PNG 字节**（含 EXIF 标记，不做转正/重编码） |
| GET  | `/` | 单页应用 |

`/api/upload` 与 `/api/load_sample` 返回的 meta 在原有
`{n,w,h,cw,x_max,boxes,feasible}` 之外，额外给出每帧
`orientations`（EXIF 方向 1–8）与 `stored_sizes`（存储方向宽高）；
其中 `w/h/boxes/feasible` 均为**转正坐标系**下的值，`boxes` 可直接与网页画布叠加。

## 已知限制

- 单会话：服务端只保存一份当前工程，多人同时用会互相覆盖（演示定位）。
- 帧数据全在内存：80 帧 × 512×512 灰度约 21MB，可接受。
- 最坏规模（80 帧、x 取值 504 个）求解约 3 秒；常规规模亚秒。
- 裁切窗垂直位置固定（按原高裁切），只有水平自由度。
